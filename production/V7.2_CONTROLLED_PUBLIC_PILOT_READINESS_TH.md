## 2. V7.2 Backend Pilot source implemented, but not deployed or verified in DEMO

**New in V7.2 branch (source-only, NOT Production):** `functions/index.js` now contains `pilotInvitationStatus` and `completePilotFreeSignup`, protected by App Check transport, exact Customer Web App ID, verified Firebase Auth identity, explicit separate `PACKTOOK_V72_PILOT_ENABLED=true` switch (defaults OFF), and an Admin-SDK-only `pilotControls/v72` Firestore document. That document is **not provisioned in Production**. The backend checks `enabled`, `legalApproved`, `ownerApproved`, approved version, exactly three maximum unique invited UIDs, a four-hour maximum UTC window, and a fresh random Pilot session ID; it rejects both V7.1 Public and V7.0 QA switches being ON.

Invited users must be **pre-created verified Auth accounts**. The Pilot activation never creates an Auth user, never exposes the allowlist and cannot overwrite a Beta/Public/QA account. It uses the existing email HMAC grant lock and atomic 15-minute/day counters, and records a once-only Free 20 grant. `uid(req)` does **not** trust the custom claim alone: a per-request server-only WeakSet proof is established only after live Firestore lease and real Auth eligibility checks, so an accidentally unwrapped new Callable cannot inherit Pilot access from a stale claim.

**Still blocked:** the Firebase Auth/Firestore V7.2 **real DEMO integration has NOT yet been run by the operator**, the web-only invited login route is NOT built, real App Check transport and Secret Manager/IAM are NOT verified, and the owner has NOT approved a release. The runtime kill switch is checked at the start of every protected request; a request already in-flight at the instant of revocation requires a separate concurrency/revocation rehearsal before any live Pilot approval.

### Existing Production architecture remains closed

**Do NOT enable the existing three Public flags for a pilot.**

Today, the V7.1 `completeFreeSignup` callable activates only when **all three** Public flags are ON; the Customer signup UI also uses the public status. The separate V7.0 QA code allows **only one** exact UID, a short-lived invite and a separate test-only consent. Neither provides a scalable but *closed* invited group with Public registration remaining OFF.

V7.2 implements the backend controls in source, but every item below still requires independent DEMO, runtime and owner verification:
1. **Server-only cohort allowlist**: suggested max 3 previously provisioned, Auth-email-verified test UIDs; do not commit UIDs, email lists, passwords or invitation links to GitHub.
2. **Distinct Pilot flag** default OFF with expiration no longer than **4 hours**, exact attested Production Customer App Check ID and a dedicated Pilot Auth claim. Expiration and revocation must be checked **on every protected request**: login, device register, reserve/finalize, status and recording access. A persistent claim alone is not sufficient.
3. **Independent Pilot activation handler**, not an unguarded use of `completeFreeSignup`, with owner-reviewed test consent and once-only Free 20 videos. Public flags must remain OFF.
4. **Dedicated hidden/noindex invite route** or explicit invitation-based sign-in, with no unguarded `createUserWithEmailAndPassword` or generic signup CTA. Pre-create invited accounts using owner-approved Auth administration **in a separate future authorization step**. A hidden page is not a security boundary: the backend allowlist is authoritative.
5. **Immediate tested revocation**: a Pilot-specific server-side kill switch that is actually checked at runtime (not merely an env variable requiring a new deployment); the revoked user must no longer use old claims for any video/credit functions.
6. **No scope creep**: existing Production Beta users, Owner, Marketing, Firestore Rules, QA, subscriptions and Omise TEST/LIVE remain isolated. Do not modify live payment systems for Free-first testing.
7. **Negative tests** for wrong UID, wrong app, wrong token/email, blocked email, expired Pilot, 4th UID, duplicate activation, cross-UID recordings, multiple devices, replay, disabled user and revoked consent.

This V7.2 PR now also adds the **source implementation** of a dedicated Pilot Callable and the DEMO test harness, but **not** a Pilot user interface, real Auth invitation provisioning, Production Pilot control document, live Secret access, deployment or owner authorization.

## 2A. V7.2 Invite-only Browser Flow — source implemented, deployment pending

The current feature branch now includes a **new, unlinked, noindex** `app/pilot-free.html`, `app/pilot-free.css`, and `app/pilot-free.js`. This is a dedicated page, **not** the existing Public signup or the V7.0 QA route. The Customer `firebase-packing-bridge.js` also recognizes the V7.2 Pilot Auth claim **only after** `pilotInvitationStatus` reports `active:true` for a live, invited, eligible session. Actual credit/device/recording calls additionally retain their independent server-side lease checks.

The Browser flow is: sign in with a **pre-created** Auth user → check exact UID/App Check with `pilotInvitationStatus` → allow an invited **unverified** Auth user to see a limited `verified:false` status → request at most one verification email per loaded page only after a fresh server invitation check → refresh Auth email state → separately accept Terms and Privacy → call `completePilotFreeSignup` → force-refresh ID token, recheck `pilotInvitationStatus.active===true`, then open `./index.html`. If a session is revoked/expired, the UI hides the PACKING button and the server blocks new protected requests. **No createUserWithEmailAndPassword, unrestricted signup, client Firestore writes, owner UID list, payment or live Omise logic is present on this page.**

The new Browser source is independently checked by `scripts/v72-pilot-browser-source-check.mjs`, mutation/negative tests in `scripts/test-v72-pilot-browser-source-safety.mjs`, and simulated DOM/Auth tests in `scripts/test-v72-pilot-browser-flow.mjs`. These are **offline tests**. The real browser, Firebase-hosted App Check transport, actual Secret Manager runtime, owner-created Pilot invitations, email delivery quotas, privacy approval and Production installation are still **NOT TESTED / NOT APPROVED**. Hiding the route / disabling indexing is not authorization; the Backend allowlist and live lease are authoritative.

Do not share a live invite link or test password in GitHub or chat. **There is no live Pilot page to visit until a separately approved, exact-scope Hosting/Functions deployment occurs.**

## 7. Operations and rollback: separate owner-reviewed deployment

Before the first pilot, record the exact immutable known-good Production revision, Git SHA, current Firebase function source/codebases, state of all Public and QA flags, approved Pilot scope, incident contact and escalation.

A rollback is **not** just `git switch`. Production deployed code and server configuration need a controlled change; claims may persist. The Pilot backend must have an independently tested runtime revocation path that blocks access even while the old ID token still contains a claim. Monitor real retry paths and Beta availability during the rehearsal.

Proposed stop triggers: unauthorized user granted access; wrong App Check app accepted; pilot expired yet usable; unexpected Free grant/regrant, negative wallet balance, cross-UID recording exposed; Beta smoke failure; alerting channel failure; or verified unusual cost growth. All should trigger an **immediate halt review** and revocation through a previously tested process. Do not assume Cloud Billing budget alerts stop spending.

## 8. External dependencies and owner decisions

- Firebase Auth with Identity Platform is needed to use Auth blocking functions. Enabling them may affect all users in this Production project. Choose **pre-provisioned invited accounts** as the initial pilot alternative, while separately reviewing Auth creation/email-abuse controls; do not upgrade Identity Platform without owner approval. Source: https://firebase.google.com/docs/auth/extend-with-blocking-functions
- Callable Functions App Check can be enforced per function with `enforceAppCheck:true`; this must be verified with a real, valid token from the exact Customer App. Source: https://firebase.google.com/docs/app-check/cloud-functions
- Cloud Billing alerts-only budgets **do not** cap spending. Any spend-cap eligibility and implications for Beta must be separately reviewed. Source: https://docs.cloud.google.com/billing/docs/how-to/budgets
- HMAC Secret Manager binding source was added in V7.1, but an actual secret resource and scoped runtime access are not proven. PDPA policy must cover anti-abuse pseudonymous indexes, cleanup, retention, erasure requests and lawful purpose.
