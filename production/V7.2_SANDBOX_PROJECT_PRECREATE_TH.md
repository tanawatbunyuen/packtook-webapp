Interpretation:
- `inventoryPass:true` means initial inputs and visible billing accounts were readable, **not approval to create**.
- `projectLookup:NOT_FOUND_UNPROVEN` is NOT proof of globally available Project ID; only actual create can confirm.
- `billingAccountListReadable:false` or permission errors may require different IAM or org context; do not try escalation on Production.
- `numberOfVisibleBudgets` is billing account level, **not** proof of a per-sandbox budget.
- A project that doesn't yet exist cannot have its project-scoped IAM, billing link, service enablement or budget validated. These stay PENDING.

## Step 2: decisions to capture BEFORE any approved sandbox writes
1. **Resource hierarchy:** select sandbox organization or folder (or an approved no-organization context), and verify the acting user has `resourcemanager.projects.create` on the parent. Never infer this permission from being Owner of Production.
2. **Billing:** select only a verified open billing account, confirm `billing.resourceAssociations.create` / billing project association permissions as applicable; get owner approval to associate NEW sandbox only. Do NOT transfer or unlink the Production billing association.
3. **Budget alerts:** before Cloud Run deployment, set a **project-scoped** budget in the billing console (illustrative monitoring target: 100 THB for this short test, customize to owner preference) with alerts at e.g. 50%, 90%, 100% and a monitored notification email; confirm permissions to create/manage budgets. A budget alert is not automatically a hard spending cap or guaranteed immediate shutdown.
4. **IAM least privilege:** sandbox creator and operator only; avoid copying IAM role bindings or Service Accounts from Production. Scope any service identities to the sandbox only. No Production Auth, Firestore, Secrets, Firebase Admin creds or payment integrations.
5. **Cloud Run / API:** after authorized sandbox creation and budget configuration, separately approve enabling Cloud Run APIs in SANDBOX ONLY; inspect quota, region `asia-southeast1`, project billing and service account permissions before creating anything.
6. **Test and cleanup:** a dedicated Cloud Run service `packtook-v72-rollback-sandbox`, two harmless revisions, A->B->A rollback evidence, no public access unless specifically justified, set max instances and avoid background workloads. Delete/disable only sandbox resources by separate approval and record end billing status.
