## C. Separate approval needed for IAM mutation

Before proposing any grant:

1. Select a **concrete future function/revision** that must access the Secret, e.g. a separately reviewed future `publicSignupStatus` or Pilot callable release. Do not deploy or add an IAM grant merely to satisfy an audit metric.
2. Identify the **intended runtime service account** explicitly in the exact-scope deployment/change design, not by guessing the default Compute/Cloud Functions identity.
3. Have an authorized administrator review the **actual principal** and Secret-level binding privately in GCP Console, including inherited/project IAM, IAM Deny, conditions, custom roles and other access paths. This script detects some openly public principals, **not all possible excessive grants**.
4. If genuinely required, request Owner's **separate approval** for one `roles/secretmanager.secretAccessor` grant on this **one Secret resource** to that **one verified service account**. Do not add a project-wide grant.
5. After approved change, inspect the policy metadata again. **Effective access requires a later authorized real runtime test** of the exact deployed revision, without printing payloads. IAM metadata alone does not prove access.

Document a rollback plan for any later permission change. The key must not be destroyed or rotated merely to undo a failed deployment because HMAC identity indexes may already depend on it.
