## 2. IAM permissions review (PROPOSALS ONLY; never automatically grant)

| Scope | Likely capability | Least-privilege design / unresolved approval |
|---|---|---|
| One Secret | `roles/secretmanager.secretAccessor` on `PACKTOOK_PUBLIC_FREE_EMAIL_HMAC_KEY_HEX` | Propose a grant **only on this Secret**, NOT on the entire project |
| Firebase Authentication | Get verified user; change custom claims | Permissions `firebaseauth.users.get` and `firebaseauth.users.update`; first investigate/test a narrowly scoped custom role. `roles/firebaseauth.admin` is broad and must not be granted automatically |
| Firestore | Transaction reads and document creation/update | `roles/datastore.user` may be required to read/write Firestore data. This grants broad entity access; Cloud IAM does not enforce collection-level Firebase Security Rules for Admin SDK, so private access review is mandatory |
| Deployment authority | Attach named Service Account to future Cloud Functions | Deployment operator needs narrowly scoped `roles/iam.serviceAccountUser` on the **target Service Account**, not assigned to the runtime itself. Review required service agents separately |

These are a **permission inventory**, NOT validated grants. The exact custom Auth role and Firestore permission set must be proven in an isolated DEMO/staging runtime test (including UID/Email Verified gating, consent, one-time free grant, App Check, Firestore transaction retries and denial paths). Never copy a generic `roles/editor`/Owner role from the current shared account.

Do not generate any Service Account JSON private keys; use GCP-managed workload identity.

## 4. Future separate changes — explicit owner approval is required for EACH

1. **`SA_ONLY`**: Owner approves creation of exactly one new Service Account with the proposed ID on `packtook-prod-01`; NO IAM grants or deployment included. Before creating, verify it does not already exist, and confirm required IAM Service Accounts API/creation permissions. No key generation.
2. **`IAM_ONLY`**: After the account exists, review/authenticate IAM least privilege and request explicit approval of the exact per-resource role bindings. Secret-level Secret Accessor is a separate permission from project/database-level Auth/Firestore permissions; roles cannot be assumed from a source test.
3. **`FUNCTION_REVISION_ONLY`**: After IAM and evidence, separately approve a precise code SHA, exact target functions and rollback. Test the new runtime identity without touching other Beta functions, with Public Signup/Access/Pilot flags still OFF. No blanket redeploy.
4. **`CONTROLLED_PILOT_GO`**: Independent real Browser App Check + Functions server enforcement, approved monitoring/billing alerts, Firebase Auth email-abuse controls, PDPA/Terms/Privacy and retention, rollback/killswitch drill, and explicit Owner signoff.
