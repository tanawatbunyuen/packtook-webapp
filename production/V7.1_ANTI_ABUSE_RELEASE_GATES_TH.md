## Changes implemented on V7.1 branch

### 1. Backend: new Free admission controls (not Auth creation throttling)

`functions/index.js` now requires *all* three existing Public flags, exact attested Customer Web App ID, and three independent admission configurations before allowing **new Free activation**:

| New environment variable | Format and allowed range | Default |
|---|---|---|
| `PACKTOOK_PUBLIC_FREE_NEW_DAY_CAP` | integer 1–1000 | zero / block |
| `PACKTOOK_PUBLIC_FREE_NEW_15M_CAP` | integer 1–100, no greater than daily limit | zero / block |
| `PACKTOOK_PUBLIC_FREE_EMAIL_HMAC_KEY_HEX` | 64 hexadecimal characters, secret 32-byte random entropy | absent / block |

**No actual secret or value was set.** These are only the code's future admission requirements; all existing Production public/QA flags remain OFF, and V7.1 code is not deployed. Initial small-pilot suggestion for owner review: 5 NEW Free grants/15m and 25/day; these limits **are not** budgets or user-identity verification.

At activation, a single Firestore transaction:
1. Checks existing account by Firebase Auth UID. For a genuine existing Public account, the request returns idempotently without resetting credits or consuming new capacity.
2. Computes HMAC-SHA256 of normalized **verified Auth email** using a protected server-only key (never browser-provided email).
3. Reads an email-claim lock `publicSignupGuards/email_v1_<HMAC>` and total new Free claims in the current 15-minute UTC bucket and UTC day.
4. Rejects a different UID that tries to claim credits for an email already used; rejects exhausted global admission buckets with `resource-exhausted`.
5. Atomically creates the email lock, increments both counters, and creates exactly one new Free account with 20 videos. All reads occur before writes; if the transaction aborts, none of these writes should commit.
6. Updates the Firebase Auth custom claim after the transaction. If this step fails, the next request returns the existing account without another grant. The existing month quota and reserve/finalize idempotency remain unchanged.

Aggregate day/15-minute documents include a provisional `expiresAt` timestamp 35 days after creation, but **auto-deletion is not active unless the owner separately configures and approves the Firestore TTL field policy**. HMAC email locks intentionally have no automatic TTL; retention and deletion basis require legal/PDPA review.

**HMAC index privacy:** the index contains a pseudonymous email-derived document ID and its owning Firebase Auth UID. This is still potentially personal information and needs privacy/retention justification and user deletion procedures. Do not rotate the HMAC secret casually: old and new indexes will no longer match, permitting regrant unless a controlled migration is completed. Never log/store the raw secret, HMAC inputs or the real email outside existing approved records.

**What this does NOT prevent:** one person signing up with multiple distinct verified email addresses; abuse of Firebase Authentication's direct `createUserWithEmailAndPassword` / verification-email endpoints before Free activation; automated calls using legitimately attested clients; fraud across changed identities. The global caps restrict credit grants/cost exposure, but can deny legitimate signups when reached. This is a controlled small-pilot design, NOT proof of public-scale capacity.

### 4. Production release prerequisites — BLOCKED

**Identity/abuse:** Current browser directly calls Firebase Auth SDK for account creation and verification emails. The activation cap cannot prevent Auth users/verification emails before activation. Decide on a documented Auth/Email abuse plan and Cloud console configuration. Firebase Authentication with Identity Platform is an **optional paid-plan-impacting upgrade** required for blocking `beforeUserCreated` and `beforeEmail` handlers, and for Firebase Authentication App Check enforcement. Do not enable these in Production without explicit approval and a staging test of all existing Beta logins. See:
- https://firebase.google.com/docs/functions/auth-blocking-events
- https://firebase.google.com/docs/auth/faq-and-troubleshooting
- https://firebase.google.com/docs/auth/limits
- https://firebase.google.com/docs/app-check

**Secret injection:** The new HMAC key must be provisioned using an owner-reviewed GCP Secret Manager / Firebase Functions secret binding and used only by the relevant signup handlers. This integration has NOT been implemented or tested as part of this source-only PR. **Do NOT paste a real key in chat, GitHub, screenshots, or command output; do not check it into `.env`.** Existing V7.1 branch code reads an environment variable, so a later exact-scoped deployment must confirm secure binding before rollout. Initial deployment cannot mark `publicAbuseReady()` true without configuration; this is intentional fail-closed behavior.

**Monitoring:** Configure in Cloud Monitoring/Logging under an explicit owner-approved runbook:
- `PACKTOOK_PUBLIC_FREE_GRANT` structured application log for *successful new* Free grants (no UID/email/IP).
- `publicSignupGuards/day_YYYYMMDD` and `window15_<bucket>` aggregate counts (Admin SDK only; Firestore Security Rules deny client writes). Maintain separate immutable audit evidence outside client-visible services.
- Alert on repeated `resource-exhausted` onboarding errors, unexpected 429-like spikes, App Check authorization failures, Firebase Auth daily creations/email verification volumes, failed Functions and Firestore transaction contention.
- Set Cloud Billing **alerts-only budget** and email notification thresholds (suggest 50%, 80%, 100% of owner-selected monthly THB limit), with service-level cost anomalies. **A budget alert does not cap spend**; it only notifies operators. See https://docs.cloud.google.com/billing/docs/how-to/budgets
- Document on-call/owner, action steps, decision to disable Public flags, and secure log retention.

**Operational limits:** The global counters are intentionally shared single documents, appropriate for a small pilot only. High concurrent writes can produce Firestore document contention; perform load tests and redesign for scale before broad marketing. See https://firebase.google.com/docs/firestore/transaction-data-contention and https://firebase.google.com/docs/firestore/best-practices

**Privacy/legal:** The approved Terms/Privacy must explicitly cover identity/email use, HMAC-derived abuse indexes, retention/erasure/objection requests, account deletion, contact and effective date. A perpetual index is not automatically PDPA compliant.

**Approval:** Public signup, Public access, Public policies approved must all stay `false` until legal signoff, secret binding, anti-abuse, real Auth/App Check, browser Free E2E, rollback plan, and owner written Go/No-Go pass. Omise Live remains OFF.
