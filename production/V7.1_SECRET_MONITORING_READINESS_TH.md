## 1. What was actually implemented in GitHub

In `functions/index.js`, Firebase Functions v2 now defines
`defineSecret("PACKTOOK_PUBLIC_FREE_EMAIL_HMAC_KEY_HEX")`. The
`publicSignupStatus` and `completeFreeSignup` callables each declare
`secrets:[PUBLIC_FREE_EMAIL_HMAC_SECRET]`. The code calls
`PUBLIC_FREE_EMAIL_HMAC_SECRET.value()` only during execution.
It **does not** read the HMAC secret directly from `process.env` or any checked-in dotenv file.

This is the **source binding only**. Secret Manager resource creation, correct
Cloud Run Functions service-account access and deployed revision have **NOT**
been done, verified or authorized.

4. In isolated DEMO/staging, verify missing/malformed secret causes Public Free

5. Prepare a separately reviewed function-specific deployment and rollback.

**Rotation warning:** HMAC-derived email indexes are permanent anti-regrant
markers. Rotating the secret without migrating prior indexes safely could
allow a second Free grant for the same email. Decide retention/deletion
requirements under Thailand PDPA before Public Pilot.

## 2. Monitoring Template — NOT APPLIED

The source now emits **PII-minimized structured log events** through
`firebase-functions/logger`:

```text
jsonPayload.message = PACKTOOK_PUBLIC_FREE_AUDIT
jsonPayload.event = new_free | duplicate_email | capacity_exhausted
jsonPayload.policyVersion = 2026-11-v1
```

The new event contains **no UID, email, IP address, HMAC value or secret**.
It is not a substitute for the platform's own logging/retention controls.
For the 2nd-gen Functions, review matching `cloud_run_revision` entries in
Cloud Logging after a separate controlled deployment. Before relying on a
filter, verify one real event appears with the expected `jsonPayload`
structure. Filters are template proposals, not proof of deployed log shape.

View and review the **non-applied** template:
`ops/v71-monitoring-proposals.json`. It proposes logs-based metrics:
- `packtook_free_new_grants`: successful new Free grants (not Auth accounts)
- `packtook_free_duplicate_email_attempts`: new UID trying an already
  used verified email
- `packtook_free_signup_capacity_denials`: admissions rejected by global caps

Add separate alerts for Firebase Authentication account creations and
verification email volume (these can occur **before** the Free grant API),
App Check failures, Cloud Run Functions error rate, Firestore contention,
Secret Manager accesses, and cost anomalies. A verified Cloud Monitoring
notification channel, owner/on-call contact, thresholds and secure log
retention plan are necessary. The attached JSON does **not** create alerts.

Relevant documentation:
https://firebase.google.com/docs/functions/writing-and-viewing-logs
https://firebase.google.com/docs/reference/functions/firebase-functions.logger

## 3. Cloud Billing Budgets — owner must decide and configure

For an initial small pilot, the operator can propose a monthly
**alerts-only** budget scoped to `packtook-prod-01`, with alert thresholds
at **50%, 80%, 100%** of a **monthly amount selected by the owner**, sent to
the actual billing administrator and designated on-call. **No THB amount
has been selected and no budget has been created**. The billing currency
depends on the actual linked billing account.

**Important:** Alerts-only budgets inform the owner and **do not cap spend**.
Google Cloud now supports optional **spend cap budgets** on a defined subset
of eligible services, including Cloud Run/Cloud Run functions in supported
situations. They require separate eligibility review; pausing Functions could
interrupt existing Beta usage. Do not enable any spend cap automatically.

Official documentation:
https://docs.cloud.google.com/billing/docs/how-to/budgets
https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps
