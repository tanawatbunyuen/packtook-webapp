# PACKTOOK V6.9.2 — Rotate Firebase App Check Web Site Key (Production)

**Goal:** Replace the current reCAPTCHA Enterprise Site Key after the Production browser returned `403 PERMISSION_DENIED: App attestation failed`.

**Important:** A new key **has not been created** by the GitHub changes. GitHub alone cannot create a Google Cloud reCAPTCHA key. This branch prepares the safe replacement and tests, without touching Production Firebase.

## 1. Create a new key in the correct project (manual)

Go to [Google Cloud Fraud Defense](https://console.cloud.google.com/security/recaptcha?project=packtook-prod-01), and confirm the active project at the top of the Console is exactly `packtook-prod-01`, not `packtook-staging` nor `packtook-prod-1`.

Create:
- Display name: `PACKTOOK-PROD-WEB-V2`
- Platform: **Web**
- Integration type: **Score-based** (no checkbox challenge)
- Domain: **packtook-prod-01-app.web.app**
- Domain verification **ON** (the "Disable domain verification" toggle must be OFF)
- Testing key **OFF**, AMP OFF, WAF not used

Alternatively, with *explicit project* in Cloud Shell:

```bash
gcloud recaptcha keys create \
  --project=packtook-prod-01 \
  --web \
  --display-name=PACKTOOK-PROD-WEB-V2 \
  --integration-type=score \
  --domains=packtook-prod-01-app.web.app
```

**Create once only.** If Google Cloud Console already created a new key, do not run the creation command again.

Google Cloud docs: https://docs.cloud.google.com/recaptcha/docs/create-key-website

## 2. Update Firebase App Check provider registration (manual)

- Firebase Console → project `packtook-prod-01` → Security → App Check → Apps
- Open `PACKTOOK Production Customer`, look at the Fraud Defense / reCAPTCHA Enterprise provider registration/edit settings
- Update that provider to use the **NEW key ID** just created. If the UI does not permit editing the key in place, follow the provider's documented unregister/re-register flow, checking current Beta traffic before and after.
- Do NOT turn on global API enforcement and do NOT change the risk threshold solely to bypass 403.
- Keep the old key temporarily for rollback. Once the new key works consistently, old key can be retired separately.

Firebase docs: https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider

## 3. Configure the new key locally in GitHub worktree

```bash
cd ~/packtook-production-v621
git status --short
git fetch origin feature/v6.9.2-recaptcha-key-rotation
git switch feature/v6.9.2-recaptcha-key-rotation 2>/dev/null || \
  git switch -c feature/v6.9.2-recaptcha-key-rotation FETCH_HEAD
git merge --ff-only FETCH_HEAD
cd production

# Offline regression with mock keys; never touches Cloud:
node scripts/test-appcheck-key-rotation.mjs

# Interactive. Paste the actual NEW public key when prompted.
# It verifies the new key via gcloud in packtook-prod-01 before editing local app/signup-config.js.
bash scripts/prepare-recaptcha-rotation.sh --production-prelaunch-only

# Review the local change. Only the public key should differ.
git diff -- app/signup-config.js

git add app/signup-config.js
git commit -m "V6.9.2: rotate PACKTOOK Production public App Check Site Key"
git push -u origin feature/v6.9.2-recaptcha-key-rotation
```

The guard refuses keys that: are identical to the old one, truncated, registered under the wrong GCP project, use unchecked global domains, do not include the exact Customer domain, are not Web SCORE, or are marked as Test Keys.

Do not paste the Site Key as a shell argument (avoid shell history). The script reads the value interactively. The Site Key is public, but **never** use API keys, Cloud credentials, service account files, payment secrets or App Check debug tokens.

## Rollback

If new key attestation fails, don't delete old GCP key. Revert Firebase App Check provider to old key and roll back **Customer Hosting only** to the matching old key release. Verify a Beta login and `publicSignupStatus` after rollback. Never roll back customer Firestore or credits for a front-end key rotation.
