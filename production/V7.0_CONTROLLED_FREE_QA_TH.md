## What V7.0 builds

1. A **server-side QA invitation**, not a public enrollment switch. Production has to explicitly set:
   - `PACKTOOK_V7_QA_ENABLED=true`
   - `PACKTOOK_V7_QA_UID=<exact Firebase Auth UID of one owner-approved test account>`
   - `PACKTOOK_V7_QA_APP_ID=<Firebase Web App ID from app/firebase-v4-config.js>`
   - `PACKTOOK_V7_QA_EXPIRES_AT=<ISO 8601 UTC expiry ending Z, no more than 48 hours ahead>`
2. QA will work **only** if the full Production project identity matches, all three Public server flags are FALSE, the Auth UID equals the allowlist, the Firebase-signed App Check token identifies the exact Customer Web App, and the lease is active.
3. `qaFreeStatus` and `completeQaFreeSignup` are new App Check-enforced callables. Email verification is checked directly via **Firebase Admin Auth**, and QA-only consent is recorded. The first verified activation writes ONE Firestore Free account and Auth claim `packtookControlledQa`.
4. Existing Beta callables accept the QA claim ONLY during the still-active invitation and with a verified App Check app ID. Ordinary Beta and Public authentication boundaries remain unchanged; Public signup remains OFF.
5. `/qa-free.html` provides **invited tester login**, email-verification link, QA consent and one-time activation. It does NOT allow public Firebase Auth account creation; the tester is provisioned by a Firebase Auth administrator first. After activation it opens the existing Packing UI so barcode video recording/credits are tested with real client code.
6. When the server QA flag or lease closes, a previously granted QA claim no longer authorizes packing. The QA account stays in Firebase until manually reviewed/deleted; no automatic deletion of real records is performed.

**Important scope distinction:** V7.0 verifies an invited-account Free onboarding path, not unrestricted public self-registration. Public self-registration still requires separate legal/operational signoff.
